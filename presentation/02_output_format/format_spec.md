# Part 2 — 출력 포맷 & SFT/DPO 데이터셋 설명

## 2-1. 정답 라벨(출력값) 포맷과 규격화 의도

### 출력 스키마 (v2 이후 고정)

모델은 **항상 아래 JSON 한 덩어리로만** 응답하도록 학습됐다. 자유 텍스트·설명·마크다운을 일절 금지한다.

```json
{
  "tasks": [
    {"id": 1, "text": "원문 그대로의 할 일"}
  ],
  "priority_order": [2, 3, 1],
  "scores": [
    {"task_id": 1, "urgency": 3, "importance": 2,
     "dependency": 1, "time_constraint": 1, "reason": "한 문장 근거"}
  ],
  "refusal_reason": "<할 일 목록이 아닐 때만 채움>"
}
```

### 4개 필드의 역할

| 필드 | 타입 | 의도 |
|------|------|------|
| `tasks` | list | 입력 할 일을 **원문 그대로** id를 붙여 보존 — 모델이 임의로 항목을 합치거나 빠뜨리는 것을 방지 |
| `priority_order` | int list | 최종 실행 순서. `tasks`의 id를 **정확히 1회씩** 포함해야 함 (누락·중복 검증 대상) |
| `scores` | list | 각 태스크의 4축 점수 + 한 문장 근거. **설명가능성(explainability)** 확보 |
| `refusal_reason` | str | 일정 관리와 무관한 입력(잡담·코딩질문 등)에 대한 거절 사유. 정상 입력 시 빈 문자열 |

### 4축 채점 기준 (각 1–5점 정수)

| 축 | 의미 | 5점 | 1점 |
|----|------|-----|-----|
| `urgency` | 마감/시작 임박도 | 오늘 마감(오전=5·오후=4·당일=3) | 마감 없음 / **이미 지난 일정** |
| `importance` | 페르소나 목표 영향도 | 결정적(에스컬레이션·위약금·법적기한 시 4–5 상향) | 옵션 |
| `dependency` | 후속 작업 블로킹 정도 | 다수 후속의 선행 입력 | 완전 독립 |
| `time_constraint` | 고정 시각 강도 | 시각 고정(회의 등) | 언제든 가능 |

### 왜 이렇게 규격화했나 — 4가지 설계 의도

1. **JSON 단일 출력 강제**: 모바일·PC 앱이 후처리 없이 바로 파싱·렌더링할 수 있어야 한다. 자유 텍스트는 앱 연동이 불가능하다.
2. **점수와 순서의 분리**: `scores`(왜)와 `priority_order`(결과)를 분리해, 점수↔순서 모순을 **후처리 ScoreRanker로 교정·검증**할 수 있다. (4축 가중합으로 순서를 재계산하는 안전장치)
3. **4축 다축 채점**: 단순 "긴급한 순서"가 아니라 긴급도·중요도·의존성·시간제약을 독립적으로 채점해, 같은 마감이라도 **에스컬레이션 리스크·선후관계**를 반영하도록 했다.
4. **원문 보존(`tasks.text`)**: 모델이 항목을 요약·병합하면 사용자가 입력한 일이 사라진다. id-텍스트 매핑을 강제해 정보 손실을 차단한다.

> **자동 채점 가능성**: 이 규격 덕분에 골격(skeleton) 규칙으로 출력의 정답 여부를 **$0·결정론적**으로 채점할 수 있다 (`verify_chosen()`). 지난 일정 순위·당일 시각 순서·체인 연속성·리스크 importance·무마감 1위 등 5종 규칙 위반을 자동 검출한다.

## 2-2. SFT / DPO 데이터셋 개형

### SFT 데이터셋 (`sft_v4_train.parquet`, 6,056행)

지도 학습은 **"이 입력 → 이 정답"** 쌍만 있으면 된다.

| 컬럼 | 설명 |
|------|------|
| `prompt` | `[OOO 씨의 오늘의 할 일 목록]` + 할 일 불릿 리스트 |
| `chosen` | 정답 JSON (위 스키마) |
| `persona` | 시스템 프롬프트에 주입할 페르소나 (예: `최여일 (포장·봉함기 조작원, 31세)`) |
| `today` | 오늘 날짜 ISO (v3부터, 상대 날짜 추론용) |
| `source` | 데이터 출처 태그 (`regen_v2`, `curated`, `refusal` 등) |

**실제 한 행:**

```
prompt:  [최여일 씨의 오늘의 할 일 목록]
         - 오전엔 구조역학 강의 듣기
         - 점심 무렵 에마랑 제이크 만나기
         - 오후엔 다니엘이랑 체스 두기
         - 교수님 천 연구실 오피스아워 들르기
persona: 최여일 (주입·포장 및 봉함기 조작원, 31세)
chosen:  {"tasks":[...4개...],"priority_order":[4,1,2,3],"scores":[...]}
```

SFT의 목적은 **"4축 JSON 포맷과 채점 규칙 자체를 모델에 주입"**하는 것이다. (없는 능력 추가)

### DPO 데이터셋 (`dpo_pairs_v5.parquet`, 1,368쌍)

선호 학습은 **"같은 입력에 대해 좋은 답(chosen) vs 나쁜 답(rejected)"** 쌍이 필요하다.

| 컬럼 | 설명 |
|------|------|
| `prompt` | (SFT와 동일) |
| `chosen` | **선호** — 규칙을 지킨 정답 JSON |
| `rejected` | **비선호** — 한 가지 규칙을 의도적으로 위반한 JSON (hard negative) |
| `category` | rejected가 위반한 규칙 유형 |
| `persona` / `today` / `source` | (SFT와 동일) |

#### rejected 위반 유형 분포 (v5, 1,368쌍)

| category | 쌍 수 | rejected가 일부러 저지른 오류 |
|----------|------|------------------------------|
| `order_score_mismatch` | 230 | 점수는 맞는데 priority_order가 점수와 모순 |
| `onpolicy` | 228 | SFT 모델이 실제로 생성한 오답 (on-policy) |
| `granularity_swap` | 220 | 마감 단위(시각 ↔ 날짜) 혼동 |
| `dependency_scatter` | 185 | 의존성 체인을 분산 배치 (연속성 위반) |
| `date_confusion` | 177 | 지난 날짜를 오늘/미래로 착각 |
| `risk_ignore` | 92 | 에스컬레이션·위약금 리스크를 importance에 미반영 |
| `past_hallucination` | 36 | 오늘 미상인데 '지났다'고 단정 |
| (refusal, category 없음) | 200 | 비일정 입력 거절 학습 쌍 (refusal_v2/*) |
| **합계** | **1,368** | |

> `onpolicy` 228쌍 세부: dependency_chain 154 · dated_mixed 41 · no_today 16 · intraday 9 · past_split 6 · relative 1 · risk 1.

> hard negative의 핵심: rejected는 **형식이 chosen과 100% 동일**하고 **단 하나의 규칙만** 틀리게 만든다. 그래야 DPO가 "포맷"이 아니라 "그 규칙 위반"만을 벌점한다.

#### 실제 chosen vs rejected diff — `date_confusion` 예시

**입력** (페르소나: 정순자, 무직 86세 / **오늘: 2026-12-11**):
```
- 10시까지 약국에 전화해서 혈압약 처방 확인 (12/11 10:00까지)
- 12월 15일 18:00까지 복지관에 프로그램 신청서 제출
- 아침에 난방기 주변 정리하고 멀티탭 점검
- 12월 9일 14:00까지 손주에게 겨울 인사 카드 써두기   ← 오늘(12/11)보다 2일 지남
- 17시까지 슈퍼에서 우유·두부 사오기 (12/11 17:00까지)
```

두 응답의 차이는 **딱 한 태스크(id=4, "12월 9일 카드")** 뿐이다:

| | priority_order | id=4 점수 | id=4 reason |
|---|---|---|---|
| ✅ **chosen** | `[1, 3, 5, 2, 4]` (4번 **최하위**) | `urgency=1, time_constraint=1` | "12월 9일 마감으로 오늘 기준 **이미 지난 일정**이므로 최하위로 배치" |
| ❌ **rejected** | `[4, 1, 3, 5, 2]` (4번 **1위**) | `urgency=5, time_constraint=5` | "마감이 **오늘**이라 즉시 착수해야 합니다" |

rejected는 "12월 9일"을 오늘로 착각해 이미 지난 카드 쓰기를 1순위로 올렸다. DPO는 이 한 쌍으로 **"오늘 날짜 기준으로 지난 일정을 식별하라"**는 선호를 모델에 주입한다.

> **포맷이 동일하고 내용 한 곳만 다르다** → 학습 신호가 "날짜 추론 규칙"에 정확히 집중된다. 이것이 hard negative 설계의 핵심이다.

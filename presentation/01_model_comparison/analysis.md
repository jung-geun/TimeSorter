# Part 1 — 4개 모델 동일 쿼리 출력 분석

> 동일한 6개 쿼리(시나리오별 대표, 의존성 체인 2개)를 4개 모델에 입력하고,
> 골격 규칙 채점기(`verify_chosen`)로 결정론적 정답을 판정한 뒤 Opus가 오류해설을 작성했다.

## 평가 대상 모델

| 키 | 모델 | 학습 단계 |
|----|------|----------|
| base | Qwen3.5-4B-Base | RLHF 미적용 사전학습 베이스 (어댑터 없음) |
| instruct | Qwen3.5-4B | instruct/thinking 모델 (어댑터 없음) |
| sft | Qwen3.5-4B + SFT v4 | 4축 JSON 포맷·규칙 지도학습 |
| dpo | Qwen3.5-4B + SFT v4 + DPO v5 | SFT 위에 선호 학습 |

## 채점 방법

각 출력을 `verify_chosen(skeleton, output)`로 채점 — 5종 골격 규칙(지난 일정 순위·당일 시각 순서·체인 연속성·리스크 importance·무마감 1위) 위반을 결정론적으로 검출. 위반 0건 = 정답(✅). Opus 하위 에이전트는 이 판정을 ground truth로 삼아 **오류의 원인만** 해설(재심 없음).

---

## ⚠️ 중요 — "instruct 0%"의 정확한 해석

instruct(어댑터 없음) 모델의 통과율 0%는 **추론 실패가 아니라 출력 스키마(포맷) 미준수** 때문이다.

- instruct는 `tasks`를 규격(`[{"id":1,"text":"..."}]`)이 아니라 **`["문자열", ...]` 형태**로 출력해 채점기 파싱이 전부 실패했다.
- 실제 추론은 합리적이었다. 예: 의존성 체인 쿼리에서 `priority_order=[5,1,3,4,2]`로 체인 ①→③→④를 **올바른 단계 순서로 연속 배치**했다(순서 자체는 정답에 근접). 하지만 스키마 위반으로 채점 단계 진입조차 못 해 ❌ 처리됐다.

> **결론**: 파인튜닝(SFT)의 1차 효과는 "없던 추론 능력 주입"이 아니라 **앱이 파싱할 수 있는 정확한 JSON 스키마 준수**다. base 모델이 instruct보다 통과율이 높은(2/6 vs 0/6) 역설도 base가 시스템 프롬프트의 스키마 예시를 더 충실히 모방했기 때문이다.

## 쿼리 #0 — (dated_mixed) : 최건호 (플랜트공학 기술자 및 연구원, 63세)

**입력**: 5개 할 일이 마감 유형별로 섞인 시나리오.
- id=1 배관 열손실 검토표 제출 (오늘 3/30 09:30 마감)
- id=2 공정안전성 검토 회의자료 초안 완성 (4/4 10:00 마감, 미래)
- id=3 현장 순회 중 펌프 진동 기록 정리 (마감 없음)
- id=4 열교환기 성능시험 결과 보고서 정리 (오늘 3/30 15:00 마감)
- id=5 부식 방지 코팅 시방 검토 의견 전달 (3/29 18:00 마감, 이미 지남)

**오늘**: 2026-03-30

**기대 정답 핵심**: 오늘 마감(id=1, id=4)을 상위로, 지난 일정(id=5)은 최하위로 강등하고 urgency·time_constraint를 2 이하로 낮춰야 한다. 미래 마감(id=2)과 마감 없음(id=3)은 그 사이에 배치.

### 모델별 결과
| 모델 | 정답 | 위반 | 오류해설 요약 |
|------|------|------|--------------|
| base | ✅ | (없음) | 형태·순위 모두 정답. ```json 펜스로 감쌌으나 파싱은 성공 |
| instruct | ❌ | JSON 파싱 실패 | tasks를 객체가 아닌 문자열 배열로 출력해 스키마 파싱 실패 |
| sft | ✅ | (없음) | 깨끗한 단일행 JSON, 올바른 스키마와 순위 |
| dpo | ✅ | (없음) | sft와 동일한 정답 출력 |

#### base — ✅
`priority_order`를 [1, 4, 2, 3, 5]로 출력해 오늘 마감 두 건(id=1·4)을 앞세우고 지난 일정 id=5를 최하위에 두었으며, id=5의 urgency=1·time_constraint=1로 골격 규칙(지난 일정→최하위·urgency/tc≤2)을 충족했다. `tasks`도 `[{"id":1,"text":...}]` 객체 배열 형태를 정확히 지켰다. 다만 출력 전체를 ```json … ``` 코드 펜스로 감쌌는데, 이 케이스에서는 후처리 단계가 펜스를 벗겨내 파싱에 성공해 통과로 판정됐다(펜스는 파서에 따라 실패 위험이 있는 형태적 약점).

#### instruct — ❌
스키마 자체가 깨졌다. `tasks`를 `[{"id":N,"text":...}]` 객체 배열이 아니라 `["배관 열손실 검토표…", …]` 처럼 **문자열 배열**로 내보내, id 키가 없어 verify_chosen이 태스크를 매칭하지 못하고 JSON 파싱(스키마 검증) 단계에서 실패했다. 내용상으로도 `priority_order`가 [1, 4, 5, 2, 3]로 지난 일정 id=5를 3순위에 올려 골격 규칙(지난 일정 최하위)을 어겼으나, 그 이전에 형태 오류로 이미 탈락이다.

#### sft — ✅
공백 없는 단일행 JSON으로 `[{"id":1,"text":...}]` 객체 배열 스키마를 정확히 지켰고, `priority_order`를 [1, 4, 2, 3, 5]로 출력해 오늘 마감(id=1·4) 상위, 미래(id=2)·무마감(id=3) 중간, 지난 일정(id=5) 최하위 순서를 맞췄다. id=5의 urgency=1·time_constraint=1로 지난 일정 강등 규칙도 충족해 위반 없이 통과했다.

#### dpo — ✅
sft와 글자 단위로 동일한 출력(같은 스키마, `priority_order` [1, 4, 2, 3, 5], id=5 urgency=1·tc=1)을 내 위반 없이 통과했다. 형태·순위·점수 모두 골격 규칙을 그대로 만족한다.
## 쿼리 #1 — intraday : 이연호 (전자제품 개발 기술자 및 연구원, 33세)
**입력**: 오늘(9/11) 마감 할 일 4건 — ①배터리 보호회로 검토본 공유(19:00), ②전원모듈 발열 데이터 보고(10:00), ③센서 펌웨어 빌드본 업로드(11:00), ④PCB 레이아웃 검토 회신(17:00)
**오늘**: 2026-09-11
**기대 정답 핵심**: 4건 모두 당일 마감(kind=today)이므로 마감 시각이 이른 순으로 정렬 → [2(10:00), 3(11:00), 4(17:00), 1(19:00)]

### 모델별 결과
| 모델 | 정답 | 위반 | 오류해설 요약 |
|------|------|------|--------------|
| base | ❌ | 17:00(태4)이 19:00(태1)보다 후순위 | 마감 시각 정렬을 무시하고 importance 위주로 배열, 늦은 마감을 앞에 둠 |
| instruct | ❌ | JSON 파싱 실패 | tasks를 객체배열이 아닌 문자열배열로 출력해 스키마 위반 |
| sft | ✅ | (없음) | 4건 당일 마감을 시각 오름차순 [2,3,4,1]로 정확히 정렬 |
| dpo | ✅ | (없음) | sft와 동일하게 시각 오름차순 정렬, 압축 JSON 단일라인 출력 |

#### base — ❌
`priority_order`를 [2,1,3,4]로 내, 10:00 마감 태스크2를 1순위에 둔 점은 맞지만 그 뒤 정렬이 마감 시각과 어긋난다. 19:00 마감(태1, time_constraint=3)을 11:00 마감(태3)·17:00 마감(태4)보다 앞에 배치해, 가장 늦은 마감을 2순위로 끌어올렸다. 이는 importance(태1=4)를 마감 임박도보다 우선시한 결과로, intraday에서는 "오늘 17:00 마감이 19:00 마감보다 후순위"라는 골격 규칙을 정면으로 위반한다. 또한 raw_output 전체를 ```json … ``` 코드펜스로 감싸 출력해 파서가 펜스 제거를 추가로 처리해야 하는 형태상 위험이 있다.

#### instruct — ❌
`priority_order`는 [2,1,3,4]로 base와 같은 마감 정렬 오류(19:00을 11:00·17:00 앞에 둠)를 안고 있으나, 그 이전에 **스키마 형태 자체가 깨졌다**. `tasks` 필드를 `[{id, text}]` 객체 배열이 아니라 `["배터리 보호회로…", …]` 순수 문자열 배열로 내보내, id 기준 검증·매핑이 불가능해 JSON 파싱(스키마 검증) 단계에서 즉시 실패했다. 점수 산정 내용을 따질 것도 없이 출력 계약(contract)을 지키지 못한 전형적 사례다.

#### sft — ✅
`priority_order`를 [2,3,4,1]로 출력해 당일 마감 4건을 10:00→11:00→17:00→19:00 시각 오름차순으로 정확히 정렬했다. 태스크2(10시, urgency=5/time_constraint=5)를 최상위로, 태스크1(19시, time_constraint=4)을 최하위로 배치해 intraday의 "이른 마감 우선" 규칙을 충실히 지켰다. tasks도 `{id,text}` 객체 배열로 내보내 스키마도 깨끗하다.

#### dpo — ✅
`priority_order`·`scores`·`reason`까지 sft와 사실상 동일한 [2,3,4,1] 정답을 출력했고, 공백 없는 단일라인 압축 JSON 형태로 스키마 검증을 통과했다. 마감 시각 오름차순 정렬 규칙을 정확히 지켜 위반 0건이며, 늦은 마감(태1 19:00)을 importance 점수와 무관하게 마지막에 둔 점이 base/instruct와의 결정적 차이다.
## 쿼리 #2 — risk : 신갑진 (철도운송 관련 종사원, 59세)

**입력**: 철도 운행 종사원의 5개 할 일 — 선로 점검 결과 시스템 등록(12/22 12:00, 미처리 시 자동 에스컬레이션), 장비 점검표 파일링, 승무원 근무일지·안전서류 관제팀 제출(12/22 15:00, 법정 기한·연장 불가), 연말 배차표 초안 업데이트(12/28 12:00), 역무실 비품 재고 확인.
**오늘**: 2026-12-22
**기대 정답 핵심**: 리스크 태스크 두 개(id=1 자동 에스컬레이션, id=3 법정 제출 기한)는 importance≥4를 받아야 하며, 오늘 마감(id=1, id=3)이 선두에, future(id=4)·none(id=2,5)이 후순위로 정렬되어야 함. 출력은 결정론적 검증기가 파싱 가능한 스키마(tasks=[{id,text}])여야 함.

### 모델별 결과
| 모델 | 정답 | 위반 | 오류해설 요약 |
|------|------|------|--------------|
| base | ❌ | JSON 파싱 실패 | 점수·순서는 합리적이나 tasks를 문자열 배열로 출력해 스키마 검증 실패 |
| instruct | ❌ | JSON 파싱 실패 | tasks 문자열 배열 스키마 위반, 게다가 id=1 importance를 4로 낮춤 |
| sft | ✅ | 없음 | 올바른 객체 스키마 + 리스크 importance=5 양호 |
| dpo | ✅ | 없음 | sft와 동일하게 정확, 리스크 importance=5 유지 |

#### base ❌
점수 자체는 리스크 인지가 양호하다 — id=1 importance=5, id=3 importance=5로 두 리스크 태스크를 모두 최상위 중요도로 평가했고 priority_order도 [1,3,2,4,5]로 오늘 마감 두 건을 앞세웠다. 그러나 `tasks`를 `[{id,text}]` 객체 배열이 아니라 원문 문자열만 담은 `["문자열", ...]` 형태로 내보내 결정론적 검증기가 task id를 매핑하지 못하고 파싱에 실패했다. 내용 판단은 맞았지만 스키마 계약을 어겨 불합격 처리된 사례다.

#### instruct ❌
base와 동일하게 `tasks`를 문자열 배열로 출력해 JSON 파싱에 실패했다. 추가로 내용 측면에서도 약점이 있어, 자동 에스컬레이션 리스크 태스크인 id=1의 importance를 5가 아닌 4로 낮추고 dependency=4·time_constraint=3 등 근거 점수도 다소 흔들렸다(id=3은 importance=5 유지). 스키마 실패가 결정타지만 리스크 강도 인식도 sft/dpo보다 보수적이다.

#### sft ✅
`tasks`를 `[{"id":1,"text":...}]` 객체 배열로 올바르게 출력해 스키마 검증을 통과했다. 두 리스크 태스크 모두 importance=5(id=1, id=3)로 정확히 평가하고 time_constraint=5를 부여했으며, priority_order=[1,3,4,5,2]로 오늘 마감 리스크 두 건을 앞세운 뒤 future(id=4)·none을 뒤로 보내 위반 0건으로 합격했다.

#### dpo ✅
sft와 동일하게 객체 스키마를 정확히 지켰고 두 리스크 태스크 importance=5를 유지했다. priority_order도 [1,3,4,5,2]로 sft와 일치하며 위반 0건으로 합격했다. 리스크 시나리오에서 sft·dpo 모두 안정적으로 스키마와 리스크 가중을 동시에 만족시킨 케이스다.
## 쿼리 #3 — relative : 민성재 (경리 사무원, 29세)

**입력**: 세금계산서 정리(다음 주 화요일까지), 2월 급여 명세서 초안 확인(내일까지), 부가세 증빙 취합(이번 주 금요일까지), 사무실 비품 재고 점검(마감 없음), 은행 이체 승인 요청서 제출(오늘 17시까지) — 총 5개 할 일.
**오늘**: 2026-02-18 (수요일)
**기대 정답 핵심**: 상대표현을 오늘 기준으로 환산해야 함 — id1 "다음 주 화요일"=2026-03-03 18:00(future), id2 "내일"=2026-02-19 18:00(future), id3 "이번 주 금요일"=2026-02-20 18:00(future), id4 마감 없음(none), id5 "오늘 17시"=2026-02-18 17:00(today). 핵심은 today 마감(id5)을 최우선에 두고, 내일·모레·다다음주 순으로 future 마감을 정렬, 마감 없는 id4를 최하위로 보내는 것.

### 모델별 결과
| 모델 | 정답 | 위반 | 오류해설 요약 |
|------|------|------|--------------|
| base | ✅ | 없음 | object 스키마 정상·priority_order [5,2,3,4,1]로 today→내일→금요일 순 정확 |
| instruct | ❌ | JSON 파싱 실패 | tasks를 `["문자열"]` 배열로 출력해 스키마 위반·파싱 불가 |
| sft | ✅ | 없음 | object 스키마·priority_order [5,2,3,1,4]로 today 우선·none 최하위 정확 |
| dpo | ✅ | 없음 | sft와 동일 정렬, 추론 reason이 더 명료 |

#### base ✅
tasks를 `{id, text}` object 배열로 올바르게 내보냈고 priority_order [5,2,3,4,1]로 오늘 17시 마감인 id5를 최우선, 내일 마감 id2, 이번 주 금요일 id3 순으로 정렬했다. 마감 없는 id4를 다음 주 화요일 마감인 id1보다 앞에 둔 점은 다소 어색하나 상대표현 환산 자체에는 결정론적 위반이 없어 통과했다. 다만 base 계열은 ```json 코드펜스로 감싸 출력하는 경향이 있어 파싱 단계에서 깨질 위험이 상존한다.

#### instruct ❌
priority_order [5,2,3,4,1]와 점수 추론은 합리적이지만, tasks 필드를 `[{id,text}]`가 아니라 `["다음 주 화요일까지..."]` 같은 순수 문자열 배열로 내보내 스키마를 위반했고 그 결과 "JSON 파싱 실패"로 채점되었다. 또한 id1 "다음 주 화요일"을 2026-02-25로, id2 "내일"의 마감 시각을 "금일 17:00 이전"으로 적는 등 상대날짜 환산도 부정확하다. 내용 추론보다 출력 스키마 자체가 깨지는 것이 instruct의 구조적 약점이다.

#### sft ✅
tasks를 object 배열로 정확히 출력하고 priority_order [5,2,3,1,4]로 오늘 마감 id5를 최우선에 두고 마감 없는 id4를 최하위로 보내 base보다 자연스러운 정렬을 보였다. 다만 reason에서 "다음 주 화요일"을 2026-02-24, "이번 주 금요일"을 2026-02-20로 적어 일부 날짜 환산이 기대 정답(03-03)과 어긋나지만, 결정론적 ground truth(violations)에서 검사하는 순서·스키마 조건은 모두 충족해 통과했다.

#### dpo ✅
priority_order [5,2,3,1,4]와 점수 분포가 sft와 거의 동일하며 스키마도 정상이다. id5 reason에 "당일 마감 업무 중 가장 임박해 최우선이다"라고 결론을 명시하는 등 추론 서술이 sft보다 한 단계 더 또렷해졌다. sft와 마찬가지로 "다음 주 화요일"의 날짜 환산은 어긋나지만 순서 정렬과 스키마가 정확해 위반 없이 통과했다.
## 쿼리 #4 — dependency_chain : 임순옥 (무직, 67세)

**입력**: 복지관 프로그램 처리 3단계 체인 — ①주민센터에 참여 문의 → ③신청서 내용 검토·수정사항 메모 → ④신청서 최종 확인 후 제출(2026-08-05 15:00 마감). 그 외 ②가족 반찬 재료 정리(독립), ⑤약국 혈압약 처방전 재발급 확인(2026-08-04 16:00 마감, today).
**오늘**: 2026-08-04
**기대 정답 핵심**: 체인 태스크 ①→③→④가 `priority_order`에서 단계 순서 그대로 **연속 배치**되어야 하고, 각 체인 단계(선행 ① 포함)의 `dependency` 점수가 **4 이상**이어야 한다.

### 모델별 결과
| 모델 | 정답 | 위반 | 오류해설 요약 |
|------|------|------|--------------|
| base | ❌ | JSON 파싱 실패 | `tasks`를 문자열 배열로 출력해 채점 스키마 파싱 불가, 평가 자체 불성립 |
| instruct | ❌ | JSON 파싱 실패 | 동일하게 `tasks` 문자열 배열 → 파싱 실패, 체인 순서는 맞았으나 채점 불가 |
| sft | ❌ | 체인 순서 불일치 + 선행 ① dependency<4 | 체인을 인지했으나 ①을 체인 뒤로 밀어 순서·연속성 깨짐, ① dep=2 |
| dpo | ❌ | 체인 순서 불일치 + 선행 ① dependency<4 | SFT와 글자 단위 동일 출력 — 체인 약점 그대로 |

#### base ❌
`tasks`를 객체가 아닌 `["문자열", ...]` 배열로 내보내 결정론적 채점기의 스키마 파싱이 실패했다(`JSON 파싱 실패`). 내용상 `priority_order=[4,5,3,2,1]`로 체인 ①③④가 인접하지 않고 흩어졌으며 ①의 dependency=2, ③=4, ④=1로 선·후행 점수도 일관되지 않다. RLHF 미적용 base 모델이라 출력 스키마 자체를 지키지 못한 전형적 사례다.

#### instruct ❌
역시 `tasks`를 문자열 배열로 출력해 파싱에 실패했다. 흥미롭게도 `priority_order=[5,1,3,4,2]`로 체인 ①→③→④가 단계 순서대로 연속 배치되어 순서 자체는 정답에 근접했으나, 스키마 위반으로 채점 단계에 진입하지 못해 ❌ 처리되었다. 즉 instruct의 실패 원인은 추론이 아니라 출력 포맷이다.

#### sft ❌
스키마는 정상 파싱됐다(`tasks`가 `{id,text}` 객체 배열). 그러나 `priority_order=[5,3,4,1,2]`에서 체인이 ③→④→①로 나와 선행 단계 ①이 후행 ③④보다 뒤로 밀려 **단계 순서 불일치**가 발생했다. 또한 선행 태스크 ①의 dependency=2로 **체인 선행 dependency≥4 요건 미달**(③=5, ④=4는 충족). SFT는 체인 존재는 학습했지만 "선행이 먼저"라는 연속·순서 제약을 내재화하지 못했다.

#### dpo ❌
`priority_order`, `scores`, dependency 값이 모두 SFT와 **글자 단위로 동일**(`[5,3,4,1,2]`, ① dep=2)하여 위반 두 건도 완전히 같다. **DPO v5가 이 dependency_chain 약점을 전혀 개선하지 못했음을 보여준다** — 선호 최적화가 다른 시나리오는 손봤더라도 체인 순서·선행 dependency 문제는 SFT 상태 그대로 남았다. 이것이 본 프로젝트의 핵심 발견이다.

### 핵심 관찰
SFT와 DPO는 동일한 `priority_order`와 dependency 점수를 산출해 동일한 두 위반(체인 순서 불일치 + 선행 ① dependency<4)으로 실패했다. 즉 DPO 단계가 체인 선행 태스크의 우선순위·dependency 처리를 SFT 대비 전혀 교정하지 못했다. dependency_chain은 모든 모델이 무너지는 공통 약점이며(base·instruct는 스키마 미준수로, sft·dpo는 추론 자체로 실패), 특히 후속 학습(DPO)으로도 풀리지 않은 미해결 과제로 남는다.
## 쿼리 #5 — dependency_chain : 이춘자 (무직, 73세)
**입력**: 가족 모임 사진 앨범 작업 체인(① 사진 정리하기 → ② 메모 고르기 → ③ 앨범 초안 완성하기, 내일 16:00 마감) + 마감 없는 장보기 + 오늘 14:00 고정 건강 상담. 입력 id 기준 체인은 id=2(1단계)→id=4(2단계)→id=3(3단계) 순으로 흩어져 배치됨.
**오늘**: 2026-07-07
**기대 정답 핵심**: 체인 3단계(id 2→4→3)를 우선순위에서 끊김 없이 연속 배치하고, 각 선행·체인 태스크의 dependency 점수를 4 이상으로 부여해야 함. 마감 없는 장보기(id=1)는 1위에 두면 안 됨.

### 모델별 결과
| 모델 | 정답 | 위반 | 오류해설 요약 |
|------|------|------|--------------|
| base | ❌ | 체인 태스크 2·4 dependency<4, 마감 없는 태스크 1위 배치 | 체인을 전혀 인식 못 해 모든 dependency=1, 마감 없는 장보기를 1순위로 올림 |
| instruct | ❌ | JSON 파싱 실패 | tasks를 객체 배열이 아닌 문자열 배열로 출력해 스키마 위반 |
| sft | ✅ | 없음 | 체인 2→4→3 연속 배치 + dependency 4/5/4로 의존성 정확 표현 |
| dpo | ✅ | 없음 | 동일하게 체인 연속 배치, 선행 단계 dependency=4 부여로 통과 |

#### base ❌
체인 구조를 전혀 포착하지 못했다. 사진 정리(id=2)·메모 고르기(id=4)·앨범 초안(id=3)이 하나의 선후 관계임을 인지하지 못해 다섯 태스크 모두 dependency=1로 평탄하게 매겼고, 그 결과 선행 태스크 2·4의 dependency<4 위반이 발생했다. 게다가 마감이 전혀 없는 장보기(id=1)를 priority_order의 1위에 올려(`[1,5,2,4,3]`) 마감 임박한 14:00 상담과 체인 마감보다 앞세우는 배치 오류까지 겹쳤다. 출력 형식은 ```json 펜스로 감싸 파싱 시 펜스 제거가 필요한 잠재적 취약점도 노출했다.

#### instruct ❌
우선순위 판단(`[5,4,3,2,1]`)과 dependency 점수(3번 2, 4번 3)에 체인을 일부 감지한 흔적은 있으나, 결정적으로 `tasks` 필드를 `[{"id":..,"text":..}]` 객체 배열이 아닌 `["문자열", ...]` 단순 문자열 배열로 내보내 스키마를 어겼다. 이 때문에 verify 단계에서 JSON 파싱 자체가 실패해 내용 평가에 진입조차 못 했다. 점수 논리의 옳고 그름을 떠나 출력 계약(schema)을 지키지 못한 전형적 instruct 실패다.

#### sft ✅
체인을 정확히 해독했다. priority_order `[5,1,2,4,3]`로 오늘 14:00 상담을 최우선에 두고, 그 뒤에 체인 1단계 사진 정리(id=2)→2단계 메모 고르기(id=4)→최종 초안 완성(id=3)을 끊김 없이 연속 배치했다. dependency도 정리 4 / 메모 4 / 초안 5로 부여해 선행 태스크 ≥4 요건을 충족, 위반 0으로 통과했다.

#### dpo ✅
sft와 동일한 priority_order `[5,1,2,4,3]`로 체인을 연속 배치해 통과했다. 다만 최종 단계인 앨범 초안(id=3)의 dependency를 1로 매긴 점은 sft(5)와 갈리는데, 검증 규칙이 "선행 태스크"의 dependency≥4만 요구하고 마지막 단계에는 강제하지 않으므로 위반으로 잡히지 않았다 — 선행 단계(id 2·4)는 모두 4를 주어 요건을 지켰다.

---
**체인은 모델 능력의 경계선이다.** 같은 dependency_chain 시나리오라도 첫 사례(#4)에서는 SFT/DPO가 실패했지만, 이 #5 사례는 둘 다 통과했다. 즉 체인 자체를 인식하느냐(base 실패), 출력 스키마를 지키느냐(instruct 실패)는 base/instruct가 못 넘는 1차 관문이고, 그 위에서 체인의 난이도·길이·배치 복잡도에 따라 SFT/DPO의 통과 여부가 갈린다. 체인 태스크는 학습된 모델조차 사례별로 결과가 흔들리는, 능력의 가장 바깥 경계선에 놓인 문제 유형임을 보여준다.
